# Test & Audit Pass — 2026-08-12

Security, backend/database, and UI/design testing across the whole app.

**Scope:** every finding below was produced against a local, disposable stack —
an ephemeral `postgres:16` container, a freshly migrated and seeded database,
and `bun run dev` on `:8080`. Production (`favapark.liara.run`) received only
five plain read-only GET/HEAD requests, listed in *Production probes*. No
signup, upload, brute-force, traversal, CSRF, or race test ever touched it.

**This is a report, not a fix.** Nothing in the application was changed. Two
new test files were added (`scripts/test-authz-coverage.py`,
`scripts/check-orphans.ts`) and are the only durable artifacts of the pass.

Every row is marked **Confirmed** (reproduced with a command and its output),
**Refuted** (the defence was probed and held), or **Inconclusive**. Findings are
separated from *documented tradeoffs* — intentional design decisions that should
not be read with the same urgency as the defects.

## What held up

These were attacked deliberately and did not break. They are the strongest part
of the codebase and worth protecting in review.

### SEC-9 — Authorization: 51/51, no gaps

The single biggest coverage gap going in. With RLS deliberately dropped, a
function missing its middleware is simply public, and this app has already
shipped two IDOR bugs (`477553e`, `86dcbcf`). Every mutating server function
across `parks`, `park-content`, `about-sections`, `attachments`, `admin-users`,
and `exhibition-api` was probed from three identities:

- anonymous → **21/21** rejected `Unauthorized: not signed in`
- signed-in non-admin → **21/21** rejected `Forbidden` / `FORBIDDEN`
- admin-only reads → **3/3** rejected
- owner-A against owner-B's rows → **4/4** rejected, including the reorder
  endpoint that `86dcbcf` fixed, using a real product id belonging to owner-B
- `revokeAdmin(self)` → blocked by `CANNOT_REVOKE_SELF`
- `saveOwnedCompany` targeting another owner's company → silent no-op, and a
  read-back confirmed the row was **unchanged** (it returns `{ok:true}`
  regardless, so "was it rejected" is the wrong question)

Now pinned by `scripts/test-authz-coverage.py`.

> **A note on how this was measured.** The first version of that script reported
> 51 passes that were not real: zod runs *before* the auth middleware, so 12 of
> the probes were rejected for having malformed payloads and never reached the
> authorization check at all. Every payload was rewritten to be schema-valid,
> and the script now classifies a schema rejection as **inconclusive** rather
> than a pass. This is exactly the false-pass shape `docs/Testing.md` describes,
> and it is worth knowing that the rule applies to any future authz test here.

### SEC-2 — Path traversal: refuted

`resolveSafePath()` holds. `..%2f`, `%2e%2e%2f`, `....//`, backslash, and
double-encoded variants against `/assets/$` all returned **404**.

An earlier run appeared to leak `package.json` — that was curl normalising the
path to `/package.json` before sending, which the **Vite dev server** serves
from the project root. With `curl --path-as-is` every attempt 404s, and
`/package.json` is **404 in production**.

### SEC-5 — CSRF: refuted

With a real signed-in browser session (`session` cookie, `SameSite=Lax`), a page
on a different origin attempted both a `credentials:"include"` fetch and a real
cross-site form POST at `saveAdminCompany`. **No row was created.** SameSite=Lax
is doing the job; there is no CSRF token, so this is the only thing doing it.

### SEC-10 — Upload extensions: refuted

`.svg`, `.html`, `.xml`, `.js` all rejected with `UNSUPPORTED_FILE_TYPE`,
against a control `.png` that was accepted — so the rejections are the
extension gate, not an unrelated failure.

### UI-4 / UI-8 — All routes, both themes, both languages: clean

14 routes × fa/en × light/dark = 56 page loads. No error boundaries, no 404s,
themes applied correctly, and heading contrast passed everywhere **including
dark theme**, which no existing test visits.

> Also worth recording: a first sweep flagged "dark theme never applied" on
> every page. That was the harness — an init script's `localStorage` writes land
> before the page's origin exists, so the app started with no preference at all.
> Writing the preference from a real page on the real origin fixed it and the
> pages were fine. It is not an app defect and should not be filed as one.

### Login page — 48 checks, one finding

Driven through the real form in a real browser, both languages, both themes,
desktop and phone. Everything below passed:

**Authentication.** Sign-up creates a session; sign-in with correct credentials
works; the mode switch between sign-in and sign-up works.

**Session cookie.** `HttpOnly`, `SameSite=Lax`, and not readable from
`document.cookie`. Remember-me (default on) issues a persistent cookie;
unchecking it issues a session cookie that dies with the browser — the two
paths in `session.server.ts:26-51` behave as documented.

**Error handling.** A wrong password and an unknown email return the *same*
message, so the form does not disclose whether an account exists. Neither
message leaks internals (no Postgres text, constraint names, or stack traces).
A duplicate sign-up through the form gets the friendly
`EMAIL_ALREADY_REGISTERED` — note this is the sequential path; the concurrent
one still leaks the raw constraint error (DB-2).

**Validation.** A malformed email and a password under 8 characters are both
blocked before submission, and neither creates a session.

**Controls.** The password visibility toggle flips the input type and reports
`aria-pressed`. The remember-me checkbox exists and defaults to checked.

**Redirect.** Role-based destination resolves correctly — an admin lands on
`/admin/exhibition`, a user with no roles on `/`. `?next=/parks` is honoured. An
already-signed-in visitor is bounced off `/auth`.

**Sign-out.** Clears the cookie **and revokes the session server-side**: the
captured token authenticated before sign-out (control) and was refused after,
so `destroySession()` really does delete the row rather than only dropping the
cookie.

**Presentation and accessibility.** Both themes apply on `/auth`; no error
boundary in any combination; no horizontal overflow at 375px and the submit
button stays visible; both inputs are labelled; the form is keyboard-reachable;
the submit button has a focus indicator; Enter submits.

Two known findings also reproduce here and are filed separately: login has no
rate limiting (**SEC-1**) and the `next` parameter is an open redirect
(**SEC-3**).

> Three initial "failures" were the harness, not the app, and are recorded so
> they are not re-investigated: the post-login redirect appeared to hang (the
> first compile of `/admin/exhibition` in dev exceeds a 10 s wait), the sign-out
> control appeared missing (it was searched for on `/auth`, which deliberately
> renders no nav, and then before the nav had hydrated), and the bottom strip of
> Persian text on the English login page is **part of the background photograph**
> (`public/img/login-day.webp`), not untranslated markup.

The original finding, as written at audit time:

### IMG-1 · High · Nothing that was ever uploaded is being served in production

Investigated after the report that images fail to load in the virtual
exhibition. Measured by browsing the live site and recording every failed
image request across `/exhibition` and all 48 company pages:

```
distinct images returning 404 : 285
  atlas import (coN-pM.jpeg)  : 133
  uploaded via admin panel    : 152
timestamped uploads still served: 0
```

**Not one uploaded file survives.** The only assets that still load are bundled
app files; every path that resolves through `UPLOAD_DIR` — the entire range of
uploads from **2026-06-22 to 2026-06-28** — returns 404. This is total loss, not
partial: `/assets/$` is functioning correctly (a bogus path 404s the same way),
it simply has nothing to serve.

The two groups arrived at that state by different routes:

**The 152 admin-panel uploads** were written through the app to what should be
the persistent disk. `liara.json` mounts the `uploads` disk at
`/app/data/uploads`, and `UPLOAD_DIR` defaults to `./data/uploads`. If the env
var is unset, wrong, or the process working directory differs, writes land on
the container's ephemeral filesystem and disappear at the next redeploy — which
matches exactly what the data shows. `docs/Operations.md` already names this as
the one operational trap in the deployment; this is that trap having been sprung.

**The 133 atlas images** never depended on an upload at all. `apply-atlas-images.ts`
set `exhibition_products.image_url` to these paths, but the bytes only reached
production by pasting a one-off script into a `liara shell`. That script has not
run against the current disk.

A fix for the second group already exists in the repo's history: commit
`18a6a5c` ("Serve imported exhibition images from the container image") baked
the 142 files in `scripts/atlas-images/` into the Docker image and added a
read-only fallback covering **135 paths** — 133 of which are exactly the ones
404ing now. That fix **was never deployed**, because the deploy workflow has
been blocked by the Actions billing issue (META-1) since before it landed.

Then commit `43e09f6` — made during this session, at the user's request, before
this symptom was known — **deleted that fallback from `main`**: `seed-assets.ts`,
the `/api/public/asset-audit` endpoint that diagnoses precisely this, and the
`COPY … ./seed-assets` line in the Dockerfile. So the fix is currently in
neither production nor the codebase.

**Two independent things to fix:**

1. **The disk (covers all 285).** Confirm `UPLOAD_DIR` in the Liara panel
   resolves to the mounted disk at `/app/data/uploads`, and that the disk is
   attached. Until this is right, every new upload is also temporary — the
   images will vanish again after the next redeploy.
2. **The atlas images (covers 133).** Either restore commit `18a6a5c`
   (`git revert 43e09f6`), which serves them from the container image and needs
   no disk at all, or re-run `scripts/apply-atlas-images.ts` against a working
   disk. The first is more durable, since it cannot be undone by a disk change.

Neither can reach production until the deploy pipeline is unblocked (META-1).

### SEC-7 · High · Live keys are permanently public *(pre-existing, not testable)*

`.env` was tracked in git until commit `385b0ff` and contained a live Supabase
anon key and a Google Maps browser key. The repo is public, so these have been
readable by anyone since the first commit and remain in history.

**This is the one item that needs action outside this repo:** rotate the
Supabase key and add referrer restrictions to (or rotate) the Maps key. History
rewriting does not undo exposure that already happened.

### SEC-1 · High · No rate limit or lockout on login

`enforceRateLimit()` exists in `src/lib/rate-limit.server.ts` but is wired only
to the assistant endpoint. [auth.functions.ts:39-56](../src/lib/auth.functions.ts#L39-L56) has nothing.

Measured: **50 consecutive wrong-password attempts, all processed**, sustained
**6.1 attempts/sec** from one client, response time flat (174 ms → 167 ms, no
backoff), and the correct password was accepted immediately afterwards — so
there is no lockout either. 10 back-to-back signups also all succeeded.

Note the asymmetry: the MFA OTP path *does* have a cooldown, a daily cap, and a
max-attempts counter. Password login has none of the three.

### SEC-3 · Medium · Open redirect after login

[auth.tsx:25](../src/routes/auth.tsx#L25) admits any `next` that starts with `/`
but not `//`. The browser's URL parser treats a backslash as a slash in the
authority position, so values the validator admits still resolve off-origin:

| `next` | validator | resolves to |
|---|---|---|
| `//evil.example.com` | rejected | — |
| `/\evil.example.com` | **admitted** | `http://evil.example.com/` |
| `/\/evil.example.com` | **admitted** | `http://evil.example.com/` |
| `/<tab>/evil.example.com` | **admitted** | `http://evil.example.com/` |

Confirmed end-to-end, not just by URL parsing: a real sign-in with
`?next=%2F%5Cevil.example.com` **landed on `http://evil.example.com/`**.

Impact is phishing — a link to the genuine site that bounces the user to a
lookalike immediately after they authenticate.

### SEC-6a · Medium · No file-size limit on any upload

None of the four upload handlers check `file.size`; each does
`Buffer.from(await file.arrayBuffer())`, holding the whole file in memory.
5 MB, 50 MB, and **200 MB** uploads were all accepted — 200 MB in 2.1 s —
writing **256 MB** to the uploads disk in a few seconds from one ordinary
company-owner account. On Liara that disk is a mounted volume.

### DB-4 · Medium · Deleting a company orphans its attachments, and the files stay public

`company_attachments.owner_id` is polymorphic with **no foreign key at all**,
and `deleteExhibitionCompanyAdmin` is a bare `DELETE` on `exhibition_companies`.

Reproduced end to end:

1. attached a document to `seed-gamma` → served at `/assets/...` (HTTP 200)
2. deleted the company as admin → `ok`
3. company row: **gone**. Its products: **correctly cascaded to 0**.
4. its attachment row: **still there**
5. the file: **still on disk and still served publicly, HTTP 200**

So an admin deleting a company reasonably believes its documents are gone; they
remain downloadable by anyone with the URL, indefinitely.

### SEC-4 · Medium · Documented security headers are not sent

README documents five headers as set in `src/server.ts`. `withStandardHeaders()`
sets only `x-request-id` and CSP. Confirmed **against production**:

| Header | Production |
|---|---|
| `x-content-type-options` | **absent** |
| `referrer-policy` | **absent** |
| `permissions-policy` | **absent** |
| `strict-transport-security` | **absent** |
| `x-frame-options` | **absent** (CSP `frame-ancestors 'none'` does cover clickjacking) |

CSP itself is correctly **enforced** in production (report-only in dev), but
carries `'unsafe-inline'` and `'wasm-unsafe-eval'` in `script-src`, which
substantially limits its value as an XSS backstop, and still allows
`https://cdn.gpteng.co` plus `*.lovableproject.com` / `*.lovable.app` websockets
left over from the Lovable integration.

### DB-2 · Low-Medium · Concurrent signup leaks the raw Postgres error

`signUp` does a `SELECT` for the email then a separate `INSERT`, not in a
transaction. Two simultaneous signups with the same email, **3 out of 3 trials**:
the loser received

```
duplicate key value violates unique constraint "users_email_key"
```

instead of `EMAIL_ALREADY_REGISTERED`. The UNIQUE constraint prevents the
duplicate row, so this is not a data-integrity problem — it is information
disclosure (table and constraint names) plus an untranslated error in the UI.
`i18n-guard` only rewrites messages containing Persian characters, so an English
Postgres error passes straight through.

### UI-10 · Low-Medium · The English UI is still laid out right-to-left

Found while auditing the login page, but it is not login-specific.

`src/styles.css:114` sets `direction: rtl` on `body` unconditionally, and
nothing anywhere sets it back — a repo-wide search for `direction: ltr` finds a
single unrelated rule for contact rows. `LangDomSync`
(`src/i18n/LanguageProvider.tsx:38-51`) switches only the `dir` **attribute** on
`<html>`, which the body's own CSS rule then overrides for everything inside it.

Measured in English mode:

| Page | `<html dir>` | computed `body` direction |
|---|---|---|
| `/` | `ltr` | **rtl** |
| `/exhibition` | `ltr` | **rtl** |
| `/about` | `ltr` | **rtl** |
| `/auth` | `ltr` | **rtl** |
| `/company/seed-alpha` | `ltr` | **rtl** |

Persian mode is consistent (`rtl` / `rtl`), so only English is affected.

Visible on the English login page: the question mark lands on the wrong side —
`?Forgot your password` and `?Don't have an account` — and the email and
password fields are right-aligned with their icons on the right, which reads as
a mirrored form to an English speaker. The Persian page is correct throughout.

This is why the earlier sweep passed: it compared `document.documentElement.dir`,
which *is* set correctly. The defect only shows in the computed style.

### VIS-1 · Low-Medium · The visual baselines cannot currently detect a regression

### DB-6 · Low · Two simultaneous first signups can both become admin

The `assign_first_user_admin` trigger checks
`NOT EXISTS (SELECT 1 FROM user_roles WHERE role='admin')` inside its own

Reproduced: **1 out of 5 trials produced 2 admins** from 2 concurrent signups on

### DB-5 · Low · Concurrent admin edits are silently last-write-wins

### DB-1 · Low · Four foreign keys were never validated

`scripts/check-orphans.ts` (added by this pass) reads `pg_constraint` directly:

### SEC-6b · Low · Upload content is never inspected

Only the filename suffix is checked. An HTML payload named `innocent.png` was
accepted, stored, and **served back byte-for-byte as `content-type: image/png`**.
The forced content-type is what keeps this low — but it is exactly the case that

### UI-1 · Low · Theme flashes light before the stored preference applies

`__root.tsx` hard-codes `data-theme="light"` in the SSR output and applies the

### DB-3 · Low · `assignCompanyOwner` is two writes with no transaction

[admin-users.functions.ts:69-80](../src/lib/admin-users.functions.ts#L69-L80)

role. Not black-box reproducible without modifying the app; reported from the

### UI-5 · Low · No accessibility tooling, no skip link

No axe-core, pa11y, or Lighthouse anywhere. No skip-to-content link exists, and
every non-standalone page renders a nav plus a floating assistant button ahead
of the content. Manual ARIA usage (`aria-label`, `role="status"`/`"alert"`,

checks it.

## Documented tradeoffs — not defects

Deliberate, documented decisions. Listed so they are not mistaken for findings.

- **Opportunistic session pruning** — expired sessions are cleaned on ~10 % of
  logins rather than by a scheduled job, wrapped in try/catch so housekeeping
  can never fail a login. Documented in `docs/Security And Auth.md`.
- **Rate limiting only on the assistant** — Postgres-backed so it works across
  cluster workers. *That it is documented does not extend to login* — SEC-1 is a
  real gap on a different endpoint, not this tradeoff.
- **No RLS** — deliberate (`0001_init.sql`), with server-function middleware as
  the compensating control. SEC-9 shows that control is currently intact.

## Fixes applied

Five findings were fixed after the audit. Each was verified by re-running the
probe that originally demonstrated it, alongside a control proving the probe
still worked — a rejection is only meaningful if the same path succeeds for a
legitimate request.

**SEC-1 — login is throttled.** `enforceRateLimit()` now guards `signIn` and
`signUp` (`src/lib/auth.functions.ts`). Three buckets: 8 attempts per account
per 5 minutes, 60 per client per 15 minutes, 5 signups per client per hour. The
per-account bucket is keyed on the email rather than the caller, because an
attacker gets a fresh IP per request while several honest users can share one;
the per-client bucket then covers spraying one password across many accounts,
which never trips a single account's counter. Attempts are counted *before* the
user lookup, so an attempt against an address with no account still consumes
allowance — otherwise the throttle itself would reveal which addresses are
registered. A correct password clears the account's bucket, so someone who
fumbles twice and then succeeds is not left locked out. `RATE_LIMITED` surfaces
as its own message (`auth.too_many_attempts`) rather than "login failed", which
would read as a wrong password and invite more attempts.
*Verified:* throttled after a handful of wrong passwords; a different account
signs in normally while the first is throttled.

**SEC-3 — the open redirect is closed.** `safeNext()` in `src/routes/auth.tsx`
resolves the candidate with `new URL(raw, origin)` and compares the origin it
actually produces, instead of pattern-matching the string. Asking the same
parser that will perform the navigation is what makes `/\host`, `/\/host` and
`/<tab>/host` fail — each starts with a single slash, so every string-level
check passes them, and each resolves off-origin. Re-checked in
`resolveDestination()` immediately before `window.location.assign`, since
`validateSearch` also runs on the server where there is no origin to resolve
against. *Verified:* all four payloads that previously escaped now stay on the
origin, and `?next=/parks` is still honoured.

**SEC-6a — uploads are capped.** `assertUploadAllowed()` in
`src/lib/storage/mime.ts` checks extension and size together, so a handler
cannot check one and forget the other, and all four upload endpoints call it.
The size is rejected from `file.size` before `arrayBuffer()`, because that call
is what pulls the upload into memory — measuring afterwards would already have
done the damage. 15 MB by default, 100 MB for video, which is the only type
that legitimately runs large. *Verified:* 60 MB image and 120 MB video rejected
with `FILE_TOO_LARGE`, a normal image still accepted, `.svg` still rejected.

**DB-4 — deleting an owner removes its files.** `purgeCompanyAssets()` /
`purgeParkAssets()` in `src/lib/storage/owner-assets.server.ts` delete the
attachment rows and unlink every stored file the owner referenced, running
*before* the owner row is deleted so the paths can still be read. It covers the
cascading rows too (gallery images, product media, logo) — those rows vanished
correctly but always left their bytes behind. External URLs are left alone.
Parks got the same treatment: the attachment table is polymorphic, so deleting
a park had the identical hole. *Verified:* an attachment served with HTTP 200
before the delete returns 404 after it.

**UI-10 — English is left-to-right.** `body` in `src/styles.css` now uses
`direction: inherit` instead of a hardcoded `rtl`, so it follows the `dir`
attribute `LangDomSync` already maintains on `<html>`. *Verified:* computed
direction is `ltr` on all five pages in English and `rtl` in Persian; on the
login page the question mark in "Forgot your password?" now lands at the end
and the fields are left-aligned with their icons on the left.

**A note on SEC-1 and migration `0004`.** Shipping the throttle broke every
sign-in in production: `rate_limit_hits` did not exist there, because `0004` had
never been applied — `docs/Operations.md` still listed `bun run db:migrate` as a
pending step, and nothing had ever surfaced that it was still pending. Users saw
"login failed" even with a correct password. Two things fixed it, and both are
worth keeping: the migration was applied, and `applyLimit()` now lets a login
proceed when the limiter itself fails rather than only when the caller is over
the limit. A feature that depends on a migration should not be able to take down
the feature it is protecting.
